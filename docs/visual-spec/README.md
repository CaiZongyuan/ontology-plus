# Visual Spec：Issue #1 的可视化需求说明与可复用 Skill

> 关联原始 Spec：[Issue #1：萃取候选逐项确认与有据数据推理](https://github.com/CaiZongyuan/ontology-plus/issues/1)。这是**文档与原型补充**，不取代 Issue 的规范定义，不代表功能已完成。

## 背景与问题

Issue #1 包含 51 条 User Stories，还规定了两轮萃取、逐项确认、合并门禁、有据 SQL 推理、模块边界、测试接缝与 Out of Scope。原文精确，适合 Agent 执行和严格验收；但人类在阅读长文本时，很难快速形成完整的**开发顺序、跨模块流转、产品操作方式、失败路径**的心理模型。

本次尝试经历了四次迭代，最后确定了可复用的产出原则：

| 版本 | 主要尝试 | 反馈与结论 |
| --- | --- | --- |
| V1 | 把规则改写成互动教程 | 明白概念却不清楚开发如何推进；不应以教程为主 |
| V2 | 将原 Spec 拆成 HTML 阶段与文字卡片 | 仍然依靠读文字，**不是**有效可视化 |
| V3 | 用有向开发依赖图、模块数据流图、合并状态关系图与 SQL 守卫路径表达逻辑 | 能直接看到大致开发流程，适合执行规格 |
| **V4** | 保留 V3 的图，增加与图同步的 UI 操作原型 | 既能理解开发依赖，也能提前看到用户实际如何操作、约束为何触发 |

设计约束：**图形负责表达依赖/流转/状态，交互负责验证规则，文字只补充必要定义与验收，不能用宣传口号填充。**

### V4 涵盖的主要交互

1. **开发 DAG**：点击阶段，查看前置与下游依赖、交付范围、测试门槛。
2. **模块数据流**：在萃取合并、数据推理等链路间切换，查看数据穿过哪些模块。
3. **源材料输入与候选审阅 UI**：切换 DDL/纯文档、查看候选来源、采纳或拒绝。
4. **合并确认 UI + 依赖图**：拒绝 `Order` 但采纳依赖它的 `SubmitOrder` 时，出现一致性错误，模拟服务端 409，图与 UI 同步更新。
5. **数据问答 UI + SQL 守卫图**：演示允许、未知表拦截、未知 JOIN 警告、没有真实数据时不编造统计结果。
6. **需求追溯**：51 条需求映射到主要实施阶段，可通过编号查看/定位；原始精确措辞仍以 Issue 为准。

### 文档的权威性与边界

- **原始 Issue 是业务/实现规则的权威来源**；HTML 是帮助沟通、理解和审阅的派生物。
- P0–P6 是根据现有依赖推导的**建议实施顺序**，不是 Issue 已确认的固定排期或完成状态。
- UI、SQL 查询、候选数据和 HTTP 反馈都属于**前端模拟**，没有接入生产系统和真实数据。
- HTML 不修改产品代码，也不引入运行时依赖；Skill 不要求在项目内新增后端服务。
- Issue 规定的浏览器/Worker、SQLite、11 模型唯一事实源、两级校验等原约束继续有效；显式 Out of Scope 的能力不在本原型中扩展。

## 后续建议使用方式

对下一份长 Spec，可让 Agent 读取中文 Skill：先核对需求和仓库结构，再选出真正适合画图的依赖关系、数据流与状态机，同时生成操作型 UI 示意，最后以需求 ID 和验收用例反查是否遗漏或错误演示。**不要机械复用本 Issue 的 P0–P6 阶段或 UI 布局。**

本次改动仅新增 Skill 与演示文档；不改变 Issue #1 的技术要求，不代替对应功能的实际实现和测试。
