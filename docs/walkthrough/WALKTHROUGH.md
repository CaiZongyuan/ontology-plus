# 真人走查脚本：从一句话描述到确认业务模型与交付（真实应用版）

供产品负责人组织规格 `#37` 第 2、3 条验收（**一位不懂技术的业务人员能否不加提示走完流程**、**是否信任 AI 助手**）使用。走查者须是一位不参与本项目、不懂软件建模与技术的业务人员。

第一部分只给主持人看，第二部分念给走查者听或打印给他，第三部分由记录人现场填写。

## 一、给主持人（不给走查者看）

### 1. 环境准备（真实应用）

先构建一次前端静态产物：

```bash
pnpm build
```

推荐为每次走查创建一个独立的空白工作目录（`ONTOLOGY_SEED_PROJECTS=0` 会跳过预置演示项目，使首页直接呈现**首次使用的三个可点选示例**，且所有操作、历史、确认状态真实写入 SQLite，刷新或重开浏览器均不会丢失）：

```bash
WALK_DIR=$(mktemp -d /tmp/onto-walkthrough-XXXXXX)
ONTOLOGY_WORKSPACE_ROOT="$WALK_DIR" ONTOLOGY_SEED_PROJECTS=0 PORT=4310 pnpm start
```

- **正式真人走查（真实大模型接入）**：
  1. 走查者入场**前**，主持人先在浏览器打开 `http://127.0.0.1:4310/?mode=llm-center#/llm-center`（或顶栏「更多 → 平台治理 → 大模型中心」），配置好可用的多模态大模型服务并点击测试连接通过（也可预先放置 `~/.pi/agent/models.json` 由服务端自动发现）。
  2. 回到走查起点地址：`http://127.0.0.1:4310/`（确认页面处于「首页」，显示“你想做一个什么样的系统？”及下方三个可点选示例卡片），使用 `1440×900` 或更大的屏幕。
  3. 全程录屏，请走查者边做边说出自己的想法（出声思考）。

- **主持人彩排 / 无网关预演（Mock 模式）**：
  若主持人在正式走查前想先自己熟悉流程，可加 `ONTOLOGY_MOCK_LLM=1` 启动：
  ```bash
  WALK_DIR=$(mktemp -d /tmp/onto-rehearsal-XXXXXX)
  ONTOLOGY_WORKSPACE_ROOT="$WALK_DIR" ONTOLOGY_SEED_PROJECTS=0 ONTOLOGY_MOCK_LLM=1 PORT=4310 pnpm start
  ```
  注意：**正式真人走查请使用真实大模型**，以便检验真实自然语言表达、追问选项和变更说明的端到端体验。

- **第 6 段（情况卡 E：“AI 服务不可用”）的切换方式**：
  主体流程（首页 → 需求 → 原型 → 业务模型 → 交付）结束后，请走查者稍候 30 秒，主持人执行以下任一操作模拟第二天 AI 服务故障：
  1. **方式一（最快，保留当前项目进度）**：主持人在新标签页打开 `http://127.0.0.1:4310/?mode=llm-center#/llm-center`，将当前启用的服务地址临时改为不可达端口（如 `http://127.0.0.1:59999/v1`）或清空密钥后保存，关闭该标签页；再递出情况卡 E，让走查者在原项目对话里继续发一句话。
  2. **方式二（若彩排时用了 `ONTOLOGY_MOCK_LLM=1`）**：在终端按 `Ctrl+C`，去掉 `ONTOLOGY_MOCK_LLM=1` 重新执行 `ONTOLOGY_WORKSPACE_ROOT="$WALK_DIR" PORT=4310 pnpm start`（因项目已保存在 `$WALK_DIR`，重启后项目仍在，且未配置密钥会真实触发「AI 服务暂不可用，请联系为你部署的人」提示）。

### 2. 主持规则

- **不提示任何操作**：不说按钮名，不说“点确认”“看左边”“在顶部切换步骤”“点撤销”。
- 走查者问“该点哪里”或“现在做什么”时，只反问：“你觉得呢？”或“你现在想做的是什么？”。
- 走查者卡住超过 **3 分钟**时，可以把下面场景里的业务事实再重复念一遍，但仍不提示界面操作，并在记录表里记下这次卡住。
- 情况卡按下面的时机递给走查者，只念卡片上的字。
- 走查者每看到一次 AI 助手改了东西，等运行结束后问一句：**“刚才 AI 助手改了什么？”**，只听和记录原话，不评价对错。

### 3. 真实应用与早期原型的区别（主持人知悉）

- 真实应用没有脚本词表限制，走查者可以用自己的自然语言描述合同管理或追问细节。
- 所有改动（需求文档、界面原型修订、业务模型）和确认记录均持久化在服务端 SQLite 中；刷新浏览器不会丢失进度或撤销历史。
- 「待更新」按直接上游逐级传递：重新确认「需求」后，先只有「原型」变为「待更新」；待「原型」更新并确认（或点击“不需要改动，按现状确认”）后，「业务模型」才会变为「待更新」。
- 「交付」步骤可以真实生成并下载不可变的开发资料包快照；「可运行系统」终点槽位在当前版本恒为“蓝图已就绪，可交付开发”。

## 二、给走查者的场景（念出来或打印）

> 你是一家制造企业法务部的负责人。公司的合同一直靠邮件和纸面流转：经常找不到最新版本，也有合同到期了没人发现。
>
> 领导希望把合同管理做成一个系统，让你先把这个系统“设计出来”，交给公司的 IT 部门去开发。你不需要懂技术。
>
> 你很清楚合同是怎么走的：
>
> - 业务部门的同事起草合同，法务审核条款，然后按金额请领导审批：10 万元以下部门负责人批；10 万到 100 万元再加财务负责人；100 万元以上再加总经理。
> - 审批通过后线下盖章，业务同事上传盖章后的扫描件，合同就归档。
> - 合同到期前 30 天提醒合同负责人，由他决定续签还是不再续签。
>
> 今天你会用一个叫 Ontology Plus 的工具。里面有一个 AI 助手。
>
> 当你觉得这份设计可以交给 IT 部门了，就告诉我。
