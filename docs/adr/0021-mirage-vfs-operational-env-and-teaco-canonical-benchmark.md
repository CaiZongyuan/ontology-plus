# Mirage VFS Operational Environment and TeaCo as Canonical Benchmark Domain

We split agent execution surfaces into three distinct runtime boundaries behind explicit ports: existing design-time `Project Steps` sessions keep their native modeling tools untouched; operational, analytics, governance, and benchmark sessions run over Mirage VFS and virtual CLIs (`@struktoai/mirage-node` + `@struktoai/mirage-pi-durable` installed as reproducible package dependencies alongside `@earendil-works/pi-durable@^1.5.2`, never imported from the gitignored `references/` directory) behind an `ExecutionEnvironmentPort`; and platform-internal application coding (`CODING` sessions for `#103`) executes through a dedicated `BuildRunner` port backed locally by a workspace-jailed Node process under `.onto-cs/workspaces/<appId>/` with command allowlists and scrubbed control-plane secrets. To validate the full `Discover → Model → Build → Operate → Evolve` loop on a realistic, externally grounded domain, we adopt Business Bench's `order-management` TeaCo case (shipping/inventory + three sequential requirement evolutions) as the single canonical validation domain, officially replacing the hypothetical milk-tea order/refund scenario in `#102` and `#103`.

## Considered Options

- **Run `CODING` sessions (`pnpm`, `vite`, `vitest`, `git`) inside Mirage's virtual shell.** Rejected: Mirage's virtual filesystem and shell cannot execute full host Node build toolchains, Playwright, or local preview servers; conflating operational VFS sandboxing with host software building creates brittle workarounds.
- **Defer Mirage VFS to an optional experiment and keep only Direct Tools.** Rejected: evaluating whether virtual filesystems and virtual CLIs reduce context and tool-discovery overhead on multi-source enterprise tasks is a primary architectural hypothesis of the TeaCo benchmark; placing Mirage behind `ExecutionEnvironmentPort` keeps Arm A (Direct Tools) and Arm B–E (Mirage VFS) fairly comparable over the same Capability Gateway.
- **Maintain both the milk-tea refund scenario (`#103`) and TeaCo in parallel.** Rejected: splitting engineering effort across two business domains duplicates reference apps, fixtures, and acceptance tests without adding architectural signal.

## Consequences

- Operational VFS mounts (`/ontology`, `/sources`, `/knowledge`, on-demand `/objects`, writable `/workspace`) and virtual CLI commands (`onto ...`) never bypass the server-side Capability Gateway or read business databases directly; all security and row-scope enforcement happens in the Gateway and business application.
- `examples/teaco/` stays permanently frozen as the verified reference application for `reference-app-validation` and `operate-campaign`, strictly isolated from `BuildRunner` workspaces used by `build-agent-campaign`.
- Public verifiers (`bb-seed0`, `teaco-dev`) live in `benchmark/verifiers/` and are blocked from all Agent VFS mounts, `Development Packages`, and `BuildRunner` workspaces; private holdout seeds and hidden oracles (`teaco-eval`, `teaco-shift`) live outside Git in `.benchmark-private/` (overridable via `BENCHMARK_PRIVATE_ORACLE_DIR`).
- Product-side benchmark reporting sits under Platform Governance (`平台治理 → 评测基准`) as a read-only consumer of archived campaign JSON reports, cleanly separated from business KPI monitoring (`数据分析中心 → 指标、场景与报告`).
- Completing the TeaCo `Discover → Model → Build → Operate → Evolve` vertical slice together with a formal projection mapping between the 11-model `Ontology Suite` and `#102`'s six core primitives (`Object / Relation / Action / Rule / Event / Goal`) satisfies `#102` in this cycle without rewriting the 11-model AST or requiring a second business domain upfront.
