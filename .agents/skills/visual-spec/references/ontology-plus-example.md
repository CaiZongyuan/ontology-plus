# Ontology Plus Issue #1：参考案例

源 Spec：[萃取候选逐项确认与有据数据推理](https://github.com/CaiZongyuan/ontology-plus/issues/1)。

## 为什么要可视化

原 Issue 有 51 条 User Stories，同时规定：两轮萃取、候选逐项确认、安全合并、SQL 依据与警告/拦截、严格的 TypeScript/browser/Worker/SQLite 约束。单纯阅读长文本不容易判断实施顺序、跨模块数据流以及 UI 行为是否符合规则。

## 建议视图（不是原 Spec 规定的唯一开发顺序）

- 开发依赖：从契约/核心纯函数起步，到 API/持久化接缝、候选审阅 UI、语义对齐、数据推理、集成验收；有据 SQL 推理是可并行开发的支线，最终在集成验收汇合。
- 数据流：`浏览器结构扫描 → ontology-core 候选/比对/合并预览 → Worker 保存任务/LLM → SQLite`；只允许 Worker 维护密钥，浏览器不需要远端调用才能做结构扫描。
- 合并状态图：候选 `新增 / 修改 / 已在工程中`；对每项采纳/拒绝；按当前工程套件做增量合并；新增的一致性错误应阻止提交（409）；不能自动连带拒绝；既有错误不阻断无关修改。
- SQL 图：`MM` 全列与 `M1`/`MM` 关联构建取数依据，匹配 `M7` SQL；未知表拒绝；未知连接警告但可继续；无真实结果不伪造数字。
- UI 演示四屏：源材料输入、候选审阅、合并确认、数据问答；在 UI 修改候选，合并图必须同步；切换 SQL 场景，守卫图必须同步。
- 验收：候选、证据、状态、当前套件合并、诊断、HTTP 409、纯文档引用、LLM 失败提示、SQL 门禁、两端中英文等。

## 明确不做

不引入图数据库、向量数据库或 Python 服务；不把 OWL/RDF 当新运行时事实源；不实现 Issue 明确排除的向量检索、跨库连接器、真值维护、完整追溯等。

## 迭代教训

- V1 将需求变成教程：理解某个机制后仍不知道开发从何开始。
- V2 将 Markdown 排版成卡片：阅读成本仍然高。
- V3 以依赖 DAG、模块流、业务状态和 SQL 连接构成“真正的图”。
- V4 将 UI 输入、候选决策、合并结果和 SQL 场景与图状态绑定，贴近最终产品的操作体验。

因此，本 Skill 不要求复制某套页面皮肤，而要求每张图和每个控件为**实施决策或验收判断**提供增量信息。
