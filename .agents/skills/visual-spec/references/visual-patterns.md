# 视觉模式：按“读者要判断什么”选图

| 读者要理解的问题 | 首选视图 | 必须可见的信息 | 合适的交互 |
| --- | --- | --- | --- |
| 开发从哪开始，哪些能并行 | 依赖 DAG / 泳道 | 阶段、边、阻塞点、交付物 | 点击阶段高亮前置/下游依赖；关联验收 |
| 一次请求穿过哪些模块 | 数据流图 / 时序图 | 调用方、模块、边界、数据读写 | 切换成功/失败链路，逐步高亮边 |
| 产品操作起来是什么样 | UI 线框 / 界面原型 | 屏幕、字段、按钮、反馈状态 | 输入、筛选、保存、切屏、返回、重置 |
| 业务规则何时阻止提交 | 状态机 / 决策树 | 当前状态、触发条件、约束、诊断 | 切换条件，实时更新路径和结果 |
| 一个改动会影响哪些对象 | 依赖关系图 / Before-After | 被改对象、引用方、冲突点 | 选择保留/删除/替换，显示断裂连线 |
| 查询能否执行，为什么 | 查询路径图 / Guard 决策图 | 可用表、JOIN 路径、警告/阻断 | 选择 SQL 场景，显示允许、警告、拦截 |
| 哪些需求已经展示与验证 | 覆盖矩阵 / 测试接缝图 | 需求 ID、所处阶段、对应 UI/图/测试 | 搜索 ID、点击定位和源文链接 |

## 组合规则

- 每个主要主题采用 **一句简短说明 → 一张具体的图 → 可以操作的 UI 或条件切换 → 对应验收**。
- 图要精简：主图展示节点/连线；详细字段在选中节点后显示。不将所有条款直接塞入 SVG 节点。
- 优先使用实体自己的术语（如“候选”“已在工程中”“一致性错误”），不要为视觉效果创造第二套业务名词。
- 正常路径与异常路径必须有明显可辨的状态变化。颜色不能是唯一提示，同时显示标签/诊断。
- 架构图描述**运行时依赖**，开发路线图描述**实施先后关系**，不要混画。

## 建议的页面布局

1. 首屏：交付范围、关键约束和主线的缩略依赖图。
2. 开发依赖拓扑：占主要宽度，节点可选，旁边是详细交付列表。
3. 按功能主线的系统流：图在上，操作示意和验证点在旁/下。
4. UI 原型：多页面切换、局部可操作控件、图文同步。
5. 需求映射与边界：筛选/折叠，不盖住主要图。

若具体 Spec 很短，可以把视图合并，**不要为了凑数量画虚假图**。
