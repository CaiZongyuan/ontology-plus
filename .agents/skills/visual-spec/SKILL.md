# Visual Spec：中文交互式开发规格

## 核心目标

把机器可执行、但人难以整体理解的长 Spec，转为**能直接看出交付范围、开发次序、产品行为和验收方式**的 HTML。

坚持四条规则：

1. **图形为主，文字为辅**。图要表达真实的依赖、状态、流转或差异；不是把段落放进卡片、给标题加图标。
2. **仍然是 Spec，不是教程**。面向实施与审阅，不做概念科普、教学任务、宣传性口号或「点击这里了解」等无信息文本。
3. **视图和原始 Spec 可追溯**。需求编号、约束、接口、测试、模型、异常路径都有源位置；精确的原始 Spec 保持不变。
4. **演示 != 产品已实现**。任何 UI/业务模拟都要显式标记为“交互原型 / 模拟数据”；不得冒充真实调用或已经实现的行为。

## 输入与取证

默认输入：GitHub Issue URL / Markdown Spec / PRD / ADR；可选输入：仓库、现有 UI 截图、技术栈、参考设计。

1. 阅读完整 Spec（含 Out of Scope、Testing、Implementation Decisions），不要只用摘要生成界面。
2. 如果提供仓库且可访问，读取 `AGENTS.md`、README、顶层目录、关键 package 入口、现有测试和 UI；**不要猜测文件路径或声称实现已存在**。
3. 建立简明的结构化提纲，区分：
   - 已确认的需求与实现约束；
   - 原系统现状及拟变更；
   - 根据依赖推导的**建议**实施顺序；
   - 验收标准、错误分支、明确不做的事。
4. 保留原始需求编号。没有编号时生成稳定的局部 ID，并回链原文标题/锚点。对不确定事实标注“待确认”，不要伪造确定性。

## 设计和实施工作流

### 1. 构建视觉信息架构

读者打开首屏应能在极少文字下回答：**交付什么、先开发什么、有哪些并行工作、怎样验收**。

优先按下列层级组织单页，而非逐段重排 Markdown：

- **范围总览**：交付主线、主要变化、硬约束、Out of Scope（短标签，避免大段解释）。
- **开发依赖图**：阶段节点与有向依赖边；节点点击可高亮前置/后续依赖，并在侧面显示该阶段的交付件、改动位置、完成标准。将可并行支线画成并行车道；不要把普通清单伪装为 DAG。
- **系统数据流 / 时序图**：展示浏览器、核心逻辑、Worker/API、持久层或 Agent 之间的数据路径；提供模式切换，显示不同链路。
- **关键业务规则图**：用状态机、前后对比、关系图或决策树表达不变量、门禁与失败路径，读者交互时画面实时变化。
- **操作型 UI 示意**：放在对应规则/流程附近，提供主要界面、真实的选择/输入/提交/反馈链，能从界面操作回看状态图。
- **验收与覆盖**：可检索的需求矩阵、测试接缝和关键失败用例；点击 ID 能定位到对应可视化与原文。

根据 Spec 复杂度有选择地使用视图，不强制生成无用图。图形选择请查阅 [视觉模式](references/visual-patterns.md)。

### 2. 对开发顺序进行推导，而不是凭感觉排列

- 从数据契约/内核纯函数 → 服务端接缝 → UI → 外部依赖 → 集成验收推导阶段。只在实际存在依赖时画连线。
- 对每个阶段写出 `输入前提 → 可并行性 → 改动范围 → 交付件 → 验收门槛`。
- 开发顺序若非 Spec 原文明确规定，统一标注 **“建议实施顺序”**。已完成/未完成状态若没有仓库或 CI 证据，**不得展示为真实进度**。
- 把技术架构图与实施路线图分开：前者表达运行关系，后者表达交付依赖。

### 3. 原型与图必须共享状态

UI 示意必须至少覆盖完整主流程及一个重要的失败/边界路径。每个操作按相同的状态驱动 UI 与对应图：

`用户操作 → 本地模拟状态 → 规则判断 → 图节点/连线更新 → 界面反馈 → 对应验收点`

例如“候选审阅 → 合并”：改变采纳/拒绝选择后，候选列表、依赖图、合并结果和诊断必须同步；拒绝被引用对象但采纳引用它的行为，应展示错误连线和新的一致性错误。**不得**仅改按钮颜色，而图和诊断不变。

例如“SQL 依据门禁”：未知表拦截；未知连接仅警告但允许继续（若原 Spec 如此规定）；缺少真实查询结果不生成统计数字。不要将这些不同策略合并成同一种“失败”。

- 一律用小规模、可读的假数据；显式标注“模拟”。
- 允许重置、切换案例；切换后所有关联视图都恢复一致。
- 对 UI、图和规则使用相同的术语和实体 ID；不要生成相互矛盾的示例。

### 4. 加入追溯和完整性检查

- 给可交互节点、原型屏幕、动作和关键验证点分配稳定 ID，并关联 Spec ID。
- 需求覆盖至少区分“在某图中呈现 / 在 UI 中模拟 / 只在文字与测试中追溯 / 本版未覆盖”；不要声称 100% 已可视化。
- 对复杂 Spec，完整的 User Stories 放在折叠的可搜索追溯区，不要占据主要图面。
- 把显式 Out of Scope 放进可查看的边界区。不要悄悄设计本来不做的功能。
- 技术细节放到点击展开区/抽屉；首屏不放全量 API、JSON、测试清单。

## HTML 输出约定

默认交付一个 `visual-spec.html`：浏览器直接打开、离线可用、自包含 CSS/JS/SVG；除非用户要求接入仓库，不引入产品运行时依赖、框架脚手架或远程 CDN。允许用原生 SVG/CSS 实现轻量图，图太复杂时可用项目已有的图组件。

视觉结构：清晰的功能分区、适量留白、可辨识的方向边、有状态的连线与节点；文本贴近图上的实际元素。优先桌面阅读，移动端不截断主要内容，复杂图允许局部横向滚动和缩放。对焦、键盘操作、动效降级、长文本折叠要可用。

**禁止以下低价值产物：**

- 把原文拆成几十张文字卡片就称“可视化”；
- 画一张静态海报，无法看出流程和依赖；
- 把需求转成给读者学习概念的 Tutorial；
- “不是逐行读 Spec”“一眼看懂未来”等无信息口号；
- 用“完成 / 已实现 / 通过”标记未被真实验证的工作；
- 用不可操作的按钮、脱离实际规则的动画营造交互假象；
- 无出处地捏造模块、文件路径、接口和产品行为。

## 最低自检门槛

制作后按 [验收与 QA 清单](references/acceptance-and-qa.md) 检查，至少做到：

1. 一张真实的依赖 DAG；一张真实的模块或业务数据流图；一个可操作 UI 场景；一个与图同步的失败/边界场景（不适合的视图需说明取舍）。
2. 节点点击影响图的高亮和对应的实施详情；UI 操作影响后续的规则模拟或结果反馈。
3. 技术范围与源 Spec 一致；抽查至少两个容易误解的异常规则；建议/已确认分开。
4. 桌面与移动端各做一轮渲染/截图，检查布局、重叠、截断；触发所有主要控件，检查 JS 错误、失效按钮和状态重置。
5. 检查 HTML 是否离线打开、是否存在外部资源请求、是否包含敏感数据；确认外链指向正确的原 Issue 和仓库位置。

## 交付回复

简要说明“有哪些图、有哪些可操作 UI 场景、哪些是模拟、如何从元素跳转到需求和验收”；提供 HTML 下载链接。若用户明确要求在 GitHub Issue 留存：优先保留原 Issue 正文，在评论里附设计背景、Skill 可访问地址、可下载 HTML、示例覆盖范围及“实施顺序为建议”的声明。**未经要求不改 Issue 正文、不改业务代码、不提交 PR。**

## 案例

参考 [Ontology Plus Issue #1 案例](references/ontology-plus-example.md)：采用“开发依赖拓扑 + 运行数据流 + 候选合并关系图 + SQL 门禁图 + 4 个可操作 UI 页面”的组合。它是范例而非固定页面模板，其他 Spec 应按自身领域选图。
